herdr fork · design note · 2026-09-18 · round 3 proposal

Native ADE

Take the coordination knowledge out of my Claude skills and memory, put it into your herdr, and hand it to whichever agent sits in a pane. Any provider, one source of truth, nothing to remember.

Today the round-table protocol lives in three Claude skills, a Python script and six of my memory notes. A Codex, Cursor or OpenCode coordinator starts blind. The fork already has the two bones this needs: the herdr --skill text is compiled into the binary, and herdr installs its own session hook into eight agent CLIs. This page is the shape I want to build on that. The open questions at the end are yours; answer by number.

Three layers, all inside the binary

01 · knowledge The text ships with herdr

Topics compiled from docs/ade/*.md in the fork. Your standing rules live in one file herdr appends at the end, so changing a model pick needs no rebuild.

  • herdr --skill upstream base, unchanged
  • herdr --skill coordinate the round table
  • herdr --skill resume pick it up cold
  • ~/.config/herdr/ade.local.md your rules
02 · delivery herdr hands it over, per provider

The agent never has to know to ask. Three channels, picked by what the CLI in the pane supports.

  • Hook: the herdr-installed session hook injects the bootstrap at start (claude, codex, cursor, copilot, agy, devin, droid, qoder already have one)
  • Typed: herdr agent start --role … types the bootstrap as the first prompt (chatgpt, dsh, anything hookless)
  • Fallback: any agent can be told to run herdr --skill coordinate
03 · operations The procedures become commands

What every coordinator and lane copies by hand today, as one verb each. Roles map to a kind and flags in config.

  • herdr lane start w2 --role lane --brief tasks/w2.md
  • herdr lane done w2 --report … --sha …
  • herdr lane waiting w2 "cloud job"
  • herdr ade checkpoint · herdr ade resume
  • [ade.roles] coordinator · lane · reviewer · critic

Left: the fork binary with the three layers. Right: the agents panel as it looks in a round, every row nested under the coordinator with the fork's parent links. The signal vocabulary stays exactly what lanes and the server push today; the commands only stop people retyping it.

Rolf-specific rules never enter the fork's git history. The compiled text is the protocol; your file is the policy on top of it, and the roles table is where "use x for y" is written down once and read by every coordinator.

A day with it

You open a Codex pane, or Cursor, or OpenCode, and say "you are the coordinator, spec first, grok xhigh for lanes". The pane already carries the bootstrap, so the agent runs herdr --skill coordinate, reads the roles table, and sees that lanes are Cursor grok xhigh with --force and that Opus lanes start at effort high. It names itself, marks the round, writes the spec brief, and starts a drafting lane with one command. Lanes end their turns with herdr lane done. The server pushes BLOCKED and GONE. At every merge the coordinator runs herdr ade checkpoint, and after round 2 lands, herdr server restart keeps every pane, turn and link, so herdr ade resume is only for a cold start.

What herdr-projects already proves

You pointed me at eliasstravik/herdr-projects: a herdr plugin, Rust, MIT, public since this morning, built for herdr 0.9.1 and up. It is the round table as a product. One coordinator conversation, a thread per task on its own worktree and branch, every brief carrying the same standing instructions and memory, reports whose ## Remember section flows back into memory, a sidebar grouped by what needs you, an inbox fed by a background ticker, adopting a pane you already started, restarting a thread whose pane is gone, threads on your saved SSH machines, pull request follow-up, and a doctor command. Its builder verified herdr's behaviour in seven recorded stages on macOS and Linux.

what it teaches the shape
  • Files are the record, prompts are nudges. The coordinator runs context at the start of every turn and re-reads state from the binary. A missed prompt loses nothing. Our DONE line typed into a pane is lost if it lands during a restart or a compaction.
  • The skill is 95 lines because state lives in the binary, not in the agent's memory. Delivery is a priming message with the command prefix, typed into the pane, so any CLI herdr can start works.
  • Data is not instructions. Reports, inbox items and command output never count as a go-ahead. The round table has no such rule yet.
  • Verified gotchas. A prompt sent while you type merges with your half-typed text and submits it, so nudges are off by default. Pane ids restart at w1 after a cold restart. The agent view filter is socket-only. Worktrees under ~/.herdr trigger Claude's trust dialog. A server not started from a login shell gives plugins a minimal PATH.
what it lacks against the round table
  • One fresh reviewer per round on a merged candidate, gates, and the two-model spec dialogue.
  • Briefs and verdicts as committed files in the repo. It keeps records in ~/.herdr-projects.
  • A roles table: thread agent is one setting, thread_agent, with a per-thread --agent override and no model or flags per role.
  • Your fork's parent nesting. It groups by project, thread and rank tokens plus a sidebar view filter.
  • GPT-6 Pro through pro-mcp, and the DONE and WAITING pushes. It watches reports and state with a ticker instead.

Open questions

Each one changes what gets built. My recommendation is in bold; say the number and a word if you agree.

  1. 1

    How much text goes into every pane at start?

    The full coordinate topic is 300 to 400 lines. Injecting it into every lane costs each worker context it never uses. Recommendation: a ten-line bootstrap in every agent pane ("you are inside herdr, pane w1F:p2; if you are told you coordinate, run herdr --skill coordinate first; if you are a lane, end every turn with herdr lane done or herdr lane waiting"), and the full topic only when a pane starts with --role coordinator or the agent asks for it.

  2. 2

    Where does the protocol text live: compiled in, or files herdr reads?

    Compiled in means the text is versioned with the fork and changes need a rebuild. Files under ~/.config/herdr/ade/ can be edited live but drift from the repo. Recommendation: compiled defaults from docs/ade/, one local override file for your rules, and a herdr ade doctor that says which is in effect.

  3. 3

    Which roles, and what are the day-one defaults?

    Recommendation: coordinator, lane, reviewer, critic, drafter, pro. Day one from your standing rules: lane, reviewer, critic and drafter are cursor -- --model cursor-grok-4.6-xhigh --force; any Claude Opus role adds --effort high; pro is chatgpt through pro-mcp. Coordinator has no default kind; it is whoever you open.

  4. 4

    Which CLIs are first-class on day one for injection at start?

    Each one is an adapter to write and test. Recommendation: claude, cursor, codex, opencode and agy through their hooks or rules; chatgpt, dsh and Grok Bot through the typed bootstrap. Copilot, devin, droid and qoder wait until you use them.

  5. 5

    Do the signal lines stay as typed prompts, or become structured events too?

    Today a lane types DONE … into the coordinator pane and that line is the record. Recommendation: keep the line exactly as it is so every coordinator reads the same thing, and have herdr lane done also stamp the pane tokens and the checkpoint file, so the record survives even if the line is missed.

  6. 6

    Delete the skills and my memory notes when round 3 merges?

    Once the topics are in the binary, the Claude skills and six memory notes are duplicates that will drift. Recommendation: yes. At the merge I remove the three skill directories and the notes, and leave one memory line: the protocol is herdr --skill coordinate.

  7. 7

    Who attacks this spec?

    The durability spec got Claude Opus at effort high as its attacker, because the round table wants two different models and the drafter is grok. Your usual pair for specs is a lane drafting and GPT-6 Pro attacking from ChatGPT. Recommendation: Pro on this one, since it is a contract that will be hard to change once shipped. Say "pro", "opus" or "grok".

  8. 8

    Command naming: one herdr ade namespace, or verbs under existing nouns?

    Upstream has herdr agent, herdr pane, herdr workspace. Recommendation: herdr lane for the lane lifecycle (start, done, waiting, close) because a lane is more than an agent, and herdr ade for the coordinator's tools (checkpoint, resume, roles, doctor). Nothing under herdr agent changes, so upstream rebases stay cheap.

  9. 9

    Native in the fork, a plugin on top of it, or herdr-projects adopted as is?

    Three ways. Adopt herdr-projects unchanged and write the round table into its PROJECT.md instructions and memory: fastest, but the reviewer round, gates, roles and your nesting stay conventions. Native in the fork as this page describes: every rebase carries it. Plugin: fork herdr-projects into herdr-ade on top of your herdr, keep its ticker, inbox, context digest, adopt, restart and remote threads, and add roles, rounds with one reviewer, gates, parent tokens and Pro. Recommendation: the plugin. The fork's own diff stays nesting plus durability, which rebases cheaply, and the coordination layer lives where herdr already expects it. The protocol text still ships as herdr --skill coordinate, printed by the plugin.
